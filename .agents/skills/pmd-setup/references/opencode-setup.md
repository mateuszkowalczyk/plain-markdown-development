# Configure the OpenCode runtime

Use this procedure only after confirming that the project uses OpenCode.

1. Confirm the project uses OpenCode V2. Inspect `.agents/pmd-runtime.md`, `.opencode/agents/`, and OpenCode configuration in both `opencode.json(c)` and `.opencode/opencode.json(c)` where present. Account for global and ancestor configuration, and for `.opencode/` configuration taking precedence over direct configuration when both are discovered. Do not treat the presence of a project file alone as proof of its effective value.
2. Ask whether to install or update the bundled runtime. Explain that it provides Coordinator, simple Builder, complex Builder, and one read-only Reviewer.
3. If declined, preserve all runtime and OpenCode files. An existing usable runtime remains valid; otherwise the main setup procedure collects alternative mappings.
4. If accepted, read every source file under `../assets/opencode/` and compare it with its target. Preserve usable identical files. Show differences and ask before replacing or materially merging divergent files whose local ownership or customization is uncertain.
5. Inspect exact model identifiers already configured in OpenCode and use the project's V2 model catalog (`/models` or `opencode models`) to find available models across providers. Where available, inspect catalog metadata for variants, capabilities, and costs (for example through the V2 model tools or `opencode api GET /api/model`). The CLI model list does not provide a `--verbose` flag. Never guess an identifier, supported variant, capability, or cost; ask when the available metadata cannot establish a suitable candidate.
6. Build a short cross-provider candidate list for each strength tier. Show two or three best-fitting candidates as `<display name> · <variant> (<provider>/<model>#<variant>) — <PMD tier>; <speed/cost note>`, omitting variant parts when none is selected. Mark uncertain classifications and cost estimates, and do not recommend uncertain candidates by default.
7. Guide the user through one model choice for each tier, one question at a time:
   1. fast and economical — Simple Builder
   2. medium, predictable, and stable — Coordinator
   3. strong — Complex Builder
   4. very strong — Reviewer
   A model may be reused across tiers.
8. Present the exact role-to-model mapping and request one confirmation before editing files. Allow role-specific corrections and reconfirm the updated summary.
9. Install the four agent templates as `.opencode/agents/pmd-coordinator.md`, `pmd-builder-simple.md`, `pmd-builder-complex.md`, and `pmd-reviewer.md`, plus `.agents/pmd-runtime.md`. Add or update exactly one concrete `model: <provider>/<model>` frontmatter field in every agent, preserving an approved variant suffix.
10. After the new runtime files are ready, remove obsolete bundled `.opencode/agents/pmd-planner.md`, `pmd-worker-simple.md`, `pmd-worker-complex.md`, and `pmd-worker.md` if present. Delete a divergent or customized obsolete file only after showing it and receiving explicit approval; otherwise report that it was retained and that it may conflict with PMD naming.
11. Set `default_agent` to `pmd-coordinator` in the effective project OpenCode configuration while preserving unrelated settings and JSON/JSONC format. If neither project configuration location exists, create `opencode.json` with the OpenCode schema declaration and `"default_agent": "pmd-coordinator"`. When both locations exist, edit the one that determines the effective default; avoid introducing a shadowed setting. Ask before replacing another configured default, including one inherited from an ancestor or global configuration.
12. Validate that the four current agents exist, frontmatter parses, every agent has one approved concrete model, no placeholder remains, the runtime maps both Builder tiers correctly, and obsolete bundled Planner/Worker agents are absent or explicitly retained because the user declined deletion. Inspect loaded configuration sources and resolved agents in the project (for example with `opencode debug config`, `opencode debug agents`, and, where available, `opencode api GET /api/agent/<agent-id>`). Confirm the effective default in a new session, that Coordinator can launch only the two Builders and the one Reviewer, that Builders cannot delegate, ask the user, stage, or commit, and that Reviewer cannot mutate files. Resolve any conflicting higher-priority configuration instead of treating a valid template as a working runtime.
13. Report the final mapping and any retained obsolete file. Have the user start a new OpenCode session to verify that `pmd-coordinator` is selected and its configured model is active. An existing session retains its selected agent and model: switching to Coordinator there does not necessarily select the model in its agent file. Explicitly select or confirm both when continuing an existing session.

Additional native or external Builder profiles may be added later as project-owned runtime customization.
